PROJECT 1Kernel Fusion Beyond 1D

cuTile  ·  GPU  ·  Tiled Attention

GPUThe Paper and Its Gap

Dodović et al., Electronics 2026

  • 4 ops: elem-add, FMA, linear+ReLU, map-reduce — all on 1D arrays
  • Plain CUDA C kernels, RTX 3080 Ti / T4 / A100
  • Memory-bound ops: 1.5×–3.13× from fusion
  • Atomic reduction: ≈ 1× — contention dominates
  • Block-level reduction: effective again, up to 2×
Paper's own future work:
"Extending the analysis to operations on multi-dimensional tensors with higher arithmetic intensity, such as matrix multiplication and convolution"
cuTile is exactly the right tool to address this — tile-level control, explicit GEMM primitives, flexible epilog fusion

GPUProblem — Attention is a Different Regime

Attention (unfused, per head):

S = Q @ K.T        # materialised  (N × N)
P = softmax(S)     # materialised  (N × N)
O = P @ V          # output        (N × D)
  • 3 kernel launches, 2 global write-read round-trips
  • N=4096, FP16: 32 MB per head — just for intermediates
  • Grows quadratically with sequence length
Paper's regime: fusion speeds up computation
(saves 33–57 % bandwidth, same result either way)
Our regime: fusion enables computation
(unfused is infeasible at long context — OOM or orders-of-magnitude slower)

Fusion benefit grows with N — qualitatively opposite of the paper's findings.

GPUProposed Solution

Fused tiled attention in cuTile
  • ct.mma for Q×KT and P×V tiles (A03 kernel as base)
  • ct.reduce for online softmax inside the tile loop
  • No N×N materialisation — O(tile) SRAM at any time
Tile loop (single kernel):
for each tile along the K-dim:
  S_tile ← Q_tile × K_tile   (ct.mma)
  update running (max, Σ) for softmax
  O_tile ← O_tile + softmax_tile × V_tile
Roofline-guided analysis
  • Compute arithmetic intensity for each variant analytically
  • Predict the crossover point before measuring
  • Use Config/Optimizer (A05) to characterise both unfused and fused
Traffic comparison:
Unfused: reads Q,K,V,S,P — writes S,P,O
Fused:   reads Q,K,V       — writes O
Eliminated: 2 × N² intermediate arrays

GPUExpected Results & Insights

Speedup grows with N At small N: similar to paper.
At large N: super-linear advantage — unfused cannot compete.
Roofline crossover Fused attention shifts from memory-bound to compute-bound as N grows — quantified by arithmetic intensity.
Tile size trade-off Optimal tile for online softmax ≠ optimal for pure matmul. New dimension of tuning vs. A03.
Key differentiator from the paper: we study fusion as a feasibility enabler, not only a bandwidth optimisation — and we address the paper's explicit open question on multi-dimensional, high-intensity operations.

PROJECT 2Light-Field Contraction on XDNA

XDNA NPU  ·  MLIR-AIE  ·  Full 8×4 Tile Array

NPUIntroduction — Bridging A06 and A10

What the course gave us:
  • A06: light-field tensor-ring contraction
    acspx, bspy → abcxy
    implemented end-to-end in cuTile on the DGX
  • A08: hand-scheduled VLIW GEMM kernel on XDNA2
  • A09: MLIR-AIE data movement, sequential c-loop
  • A10: full 8×4 NPU, spatial broadcasting of inputs
The question:

Can we run the same A06 contraction
on the full XDNA NPU?

GPU reference exists → direct performance comparison.
All building blocks are in place.

NPUProblem — Mapping an Irregular Einsum to XDNA

Dimension classification of acspx, bspy → abcxy:

Type Dims Role
M / Nx, youtput spatial
Ks, pcontracted (inner)
Ca, b, cbatch (outer)
  • NPU kernel expects fixed layout: prmk × rqkn → pqmn
  • K-dims s, p are not aligned to NPU's r, k tile structure
  • C-batch dims a, b, c need loop orchestration across the tile array
Open design questions:
  • How to decompose the multi-K contraction into XDNA-compatible GEMMs via Config/Optimizer?
  • Which of x, y maps to NPU columns vs. rows — and which input should be broadcast along which axis?
  • Padding overhead for non-power-of-2 s, p dimensions?
  • How do the a, b outer loops interact with the A10 broadcasting scheme?

NPUProposed Solution

Decomposition & kernel
  • Config/Optimizer (A05): classify s, p as sequential K-dims, decompose into XDNA-compatible GEMM sequence
  • Reuse A08 VLIW tensor kernel for the inner matmul tile (no changes needed)
  • Sequentialise over c (A09 pattern), parallelise x, y spatially across the 8×4 grid
MLIR-AIE data movement
L3   → shim DMA    full tensors acspx, bspy
↓                     tile + broadcast for x (cols), y (rows)
L2   → object FIFO  A10 broadcast pattern
↓                     prmk / rqkn tiles per compute tile
L1   → VLIW kernel  A08 matmul + accumulate
↑                     join column outputs (A10 pattern)
L3   ← shim DMA    output abcxy

NPUExpected Results & Insights

TFLOPS comparison Direct apples-to-apples: NPU vs. A06 cuTile GPU result on the same contraction and data.
Bottleneck analysis Hypothesis: data movement for s, p padding dominates over compute on the NPU.
Spatial dim selection Which assignment of x, y to rows/cols minimises DMA volume? Insight into the A10 broadcasting trade-off for non-square contractions.
Core insight: this contraction was never designed for NPU execution. We will quantify the mismatch between the XDNA's fixed GEMM layout and the natural tensor structure of the light-field decomposition — and measure whether spatial parallelism closes the gap.
